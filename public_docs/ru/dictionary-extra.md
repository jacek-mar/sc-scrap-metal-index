## Практическое чтение полей

См. [Использование поиска](using-the-search.md): пример Nebula GS и значения
всех шести статусов названия. Текстовый ключ — код для поиска названия в
языковой таблице игры. Собственное поле определения — хранимое у предмета
значение, указывающее на ключ. Известный префикс ключа — фиксированная часть,
добавляемая перед кодом для поиска названия. Общий подтип — группа родственных
предметов с общим названием; оно помечается `category`. Пространство ID —
отдельная система нумерации: `storeId`, `storeItemId`, `atlasId`, `iid` и `vid`
не взаимозаменяемы.

`<WinUser>` — заполнитель имени пользователя Windows локального сервера,
а не буквальный текст в имени базы данных. Оператор может настроить другое имя.
`[]` означает каждый элемент списка. `<>` — наблюдавшийся числовой слот;
используйте слот собственной записи. Физическая строка — реальная строка
штатного файла, включая комментарии и пустые строки.

`iid` ссылается на экземпляр предмета внутри учётной записи, а `vid` — на
экземпляр корабля. Не копируйте в эти поля ID каталога. Упакованные слова атласа
содержат ещё не расшифрованные закодированные значения: не читайте их как
обычные ID предметов. Ненаблюдавшиеся поля `autogenItems` — лишь возможные
места хранения, а не подтверждённое описание их элементов или инструкция по правке.

Область учётной записи — классификация, а не доказательство работоспособности
или безопасности выдачи предмета. Места возможного хранения по типам
перечислены в `data/db_by_kind.csv` (ниже); столбец `db_fields` только
подтверждает наблюдение предмета в образце базы данных. Безымянный предмет
ищите по `defName`. Для общего `storeItemId` включите все определения
и изучите каждую совпавшую строку; никогда не выбирайте первую автоматически.
Тип и defName вместе определяют строку.

Описание может отсутствовать, если подходящего текста нет, он длиннее
200 символов или является художественным текстом (включая совпадения с ним).
Обрезки нет. `$value$` — значение, заполняемое игрой из определения;
выгрузка его не вычисляет. Например, `$projectile_speed_mul$%` —
не числовая характеристика в этом наборе данных.

## Значения диагностических признаков

| Признак | Значение для оператора |
|---|---|
| `ambiguous_defName_across_kinds` | Код встречается в нескольких типах; сохраняйте тип вместе с ним. |
| `cant_be_bought` | Штатное определение запрещает покупку; это не доказывает безопасность выдачи. |
| `no_name` | Исходный реестр не содержал названия; последующий поиск мог его найти. |
| `no_store_entry` | Соответствующая запись магазина не найдена; не предполагайте доступность в магазине. |
| `unresolved_storeItemId_expression` | ID — выражение, не вычисленное статическим средством чтения. |
| `xml_only` | Запись найдена только в XML, а не в определении Lua. |

## Файлы поиска

Страница поиска использует компактные строки-массивы в `site/data/items.js`
(учётные записи) и `items_all.js` (необязательный полный набор). Фиксированный
порядок: kind, defName, name_en, name_ru, label_en, label_ru, name_status,
storeItemId, storeId, atlasId, account_scope. Скрипты сведений по типам
содержат остальные столбцы; ключ — defName внутри типа. Загружаемый по запросу
каталог общих ID содержит пары kind и defName из всех определений, чтобы
предупреждения включали внутренние записи без загрузки полного поискового
индекса. Файлы воспроизводят загружаемые данные с теми же 24 столбцами. Скрипты путей по типам (`site/data/locations-<kind>.js`)
и таблица базы данных (`site/data/db.js`) загружаются по запросу.

## Пути в файлах (`data/locations.csv`)

Одна строка на каждое место появления предмета в штатных файлах: `kind`,
`defName`, `group`, `location` (стандартный путь установки и физическая строка),
`role` (словесное пояснение), `referrer` (ссылающийся предмет или таблица, если есть).

| group | Значение для редактирования |
|---|---|
| `edit_here` | Исходное определение предмета и собственные поля в `data\gamedata` — изменять здесь. |
| `generated` | Копия в `cloud\data`, записываемая `prepare_shared`; ручная правка будет потеряна при следующей подготовке серверных данных. |
| `server_rules` | Редактируемый вручную серверный файл в `cloud\data`, например `store_rules.xml`. |
| `inert` | Файл, не читаемый ни одной службой (`defmod_rules*.xml`); правка не действует. |
| `used_by` | Другой предмет или таблица со ссылкой на предмет: `role` поясняет роль, например «требуется как корабль для», «установлен по умолчанию на», «в пресете модулей», «выпадает из таблицы добычи», «результат чертежа», «содержится в наборе», «базовое определение для», «компонент изготовления для». |

Перед удалением или переименованием предмета проверьте его строки `used_by`:
каждая ссылается на прежнее имя.

## Пути в базе данных по типам (`data/db_by_kind.csv`)

Где могут храниться предметы каждого типа в игровой базе данных
(`cosmosim_<WinUser>`): `kind`, `database`, `collection`, `field_path`,
`value_written` (записываемое значение: defName, числовой ID или ID экземпляра),
`evidence` (S — наблюдалось в образце базы данных, D — документированная схема,
B — имя поля в серверной программе, M — тип почтового вложения,
L — наблюдалось после выдачи на тестовом сервере), `mail` (как отправить
по почте, если возможно). В конце добавлены `value_written_ru` и `mail_ru` —
русские версии этих пояснений; при пустом русском тексте сайт использует
английский. Имена полей и коды почтовых типов не переводятся.
Строки с пометкой «не проверено» — наводки, а не подтверждённые форматы.
Базы истории боёв и статистики (`games_*`, `stats_*`, журналы, таблицы лидеров)
в этой версии не охвачены.

Три неочевидных особенности: установленный модуль хранится на корабле по `iid`,
а не по имени (`vessels[].equipped[]`); боеприпас использует поле `def`,
а не `defName`; ресурсы изготовления хранятся как ключи `craftResources`,
а количество — как значение.
